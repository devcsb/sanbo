# 산보 v0.9.4 후속 비판적 검토

검토일은 2026-10-25이며 기준 소스는 `4b64b2c80ed099d697a59174347486b49ff71573`이다.
배포 소스 `b10d7e2334616b401bd2c2c13236dc757b337d07` 이후에는 배포 증거 문서만 바뀌었다.
이 문서는 새로운 검토 결과다. 수정 완료나 추가 배포를 뜻하지 않는다.

## 결론

추가 개선이 필요하다. 작은 백업 파일로 기록 화면의 집계가 실패하는 문제를 재현했다.
Android 파일 선택기에서는 앱의 크기 검사보다 먼저 큰 메모리 할당과 파일 복사가
실행된다. 원본 위치를 클립보드에 즉시 복사하는 경로와 보관 정책의 설명도 보완해야 한다.

이번 조사에서 원격 코드 실행, 계정 탈취, 서명 개인키 탈취를 입증한 것은 아니다.
백업 공격은 사용자가 파일을 선택하고 가져오기를 승인해야 한다. 클립보드 노출도
사용자가 데이터 복사를 눌러야 한다. 실제 사용자 기록이나 CARTO 사용량을 공격에
사용하지 않았다.

## 범위와 증거 수준

- 백업 코덱 → 파일 선택 플러그인 → 저장소 → 기록 화면 → 재계산 경로를 추적했다.
- GPS 필터, 거리 집계, 고속 제외, 위치 수집 복구, 건강 권한, 지도 통신, native
  manifest, 공유, 삭제, CI와 배포 검사 도구를 위험 중심으로 읽었다.
- 격리된 메모리 SQLite와 합성 위치로 새 진단 7개를 실행했다. 7개 모두 현재 문제
  동작을 확인했다. 보안 회귀 테스트가 통과했다는 의미가 아니다.
- Dart 잠금 파일의 hosted 패키지 125개를 OSV Pub API에 실제 조회했다. 일치 항목과
  추가 페이지는 0개였다. Flutter 엔진, OS SQLite, Gradle/Maven, CocoaPods, 새로운
  미공개 취약점까지 검사한 결과는 아니다.
- 사용자 지침에 따라 직접 조사했다. 별도 모델이나 외부 업체의 독립 감사가 아니다.
- 이전 배포의 전체 통과 게이트와 실제 기기 설치 검사를 반복하지 않았다. 이번에는
  제품 코드 변경, 앱 설치, 사용자 DB 변경, 키나 요금제 변경, 배포가 없었다.

원시 진단과 결과는 저장소 밖 `~/.local/share/sanbo-security-audit/2026-10-25/`에
보관했다. 합성 입력만 사용했고 실제 위치, 키, 계정 정보는 포함하지 않았다.

## 발견 사항

P1은 다음 변경에서 먼저 처리할 항목, P2는 후속 개선 항목이다. CVSS 등급은 아니다.

| 우선순위 | 문제 | 증거와 영향 |
|---|---|---|
| P1 | 복원한 집계값으로 기록 화면이 실패한다 | 625바이트 백업의 두 세션에 큰 정수 시간을 넣으면 가져오기는 성공하고 `completedStats()`는 SQLite `integer overflow`로 실패한다. `completedHistoryProvider`가 목록과 집계를 함께 반환하므로 정상 기록 목록까지 오류 화면으로 가는 코드 경로가 있다. 별도 두 세션의 유한한 거리 `1e308`은 합계 `Infinity`가 됐다. |
| P1 | Android의 50MB 검사가 너무 늦다 | `PlatformBackupFileService.pick()`의 검사 전에 고정된 `file_selector_android 0.5.2+9`가 제공자의 SIZE로 `new byte[size]`를 할당하고 `readFully`를 실행한다. 이어 파일을 캐시에 제한 없이 다시 복사한다. 큰 파일이나 잘못된 metadata로 메모리/디스크/화면 응답에 문제가 생길 수 있다. 소스에서 확인했으며 기기를 실제 OOM으로 종료시키지는 않았다. |
| P1 | 작은 백업의 시간 범위가 계산량으로 확대된다 | 409바이트로 1,000년짜리 산책을 가져올 수 있었다. 이 범위는 525,948,480분이다. 제외 취소 등의 재계산은 분마다 객체를 생성한다. 안전한 7일 예제로 입력 window 0개가 10,080개로 늘어나는 것을 45ms에 확인했다. 1,000년 확대는 실행하지 않았고 예상 소요 시간도 추정하지 않았다. |
| P2 | 정밀 경로와 메모가 안내 없이 클립보드에 들어간다 | 실제 상세 화면을 띄운 위젯 진단에서 데이터 복사 버튼 1회로 GPS/메모가 `Clipboard.setData`에 전달되고 확인창은 없었다. Android 최소 버전은 API 26이므로 구형 OS의 백그라운드 클립보드 접근도 고려해야 한다. 외부 악성 앱으로 데이터를 훔치는 시험은 하지 않았다. |
| P2 | 저장하지 않았다고 안내한 실패 기록을 내부에는 보관한다 | `finalizeDiscardedSession`은 원본 좌표를 저장한다. 진단에서는 숨겨진 좌표 1개가 남지만 기록 목록과 전체 백업에는 0개였다. `stop()`은 이 경로에서 ‘산책을 저장하지 않았어요’라고 안내한다. 사용자의 명시적 ‘기록 지우기’는 실제로 세션을 삭제하므로 그 기능과 혼동하지 않는다. |
| P2, iOS 공개 전 | ‘이 기기에만 저장’이 iOS OS 백업까지 설명하지 못한다 | DB는 `Documents/sanbo.db`에 있으며 앱 코드와 사용 중인 path_provider에 백업 제외 설정이 없다. Apple 문서는 Documents를 기본 백업 대상으로 설명한다. iCloud 설정에 따라 복사될 수 있다는 소스 기반 판단이며 실제 iCloud 전송은 확인하지 않았다. Android에는 별도 백업 제외 규칙이 있다. |
| P2, 측정 별도 설계 | 정지 중 GPS 흔들림을 걸음으로 누적할 수 있다 | 정지 상태를 가정하고 10초마다 약 20m 왕복, 정확도 30m, provider speed 0인 합성 입력을 주면 180초에 360.3m, 이동 180초로 집계됐다. 지금의 1.5m 바닥값과 150m 정확도 기준은 이 입력을 거르지 못한다. 실제 기기에서 같은 오차가 발생했다는 증거는 아니다. |

### 백업 입력과 집계 실패

근거 파일은 `lib/data/walk_repository.dart`의 `_validatedSessionRow`, `_requiredInt`,
`_requiredDouble`, `completedStats`와 `lib/features/history/history_providers.dart`다.
현재 검사는 음수와 비유한 숫자를 거부하지만, 개별 값이 유한하더라도 합산이나
초→마이크로초 변환에서 안전한지는 확인하지 않는다. 저장한 시간과 실제 시작/종료
범위도 연결하지 않는다. 파일 크기 제한과 SQL 바인딩은 이 오류를 막지 못한다.

`backup_boundary_probe_test.dart`에서 다음을 각각 확인했다.

1. 큰 정수 시간 2개를 성공적으로 가져온 뒤 합계 계산 실패. 개별 목록 조회는 성공.
2. 큰 유한 실수 거리 2개의 합계가 무한대가 됨.
3. 천 년 범위의 입력 수락. 재계산 실행은 의도적으로 생략.
4. 짧은 입력이 재계산에서 7일치 분 객체로 확대됨.

이 파일은 서명된 백업이 아니므로 정상 범위 값의 조작까지 막을 수는 없다. 목표는
외부 입력이 앱의 가용성과 저장소 무결성을 깨지 않도록 하는 것이다.

### 파일 선택 경계와 불필요한 사본

실제 잠금 버전의 `FileSelectorApiImpl.java`의 `toFileResponse()`를 읽었다.
파일 크기가 알려져 있지 않으면 null을 반환하므로 정상 클라우드 문서도 취소처럼
보일 수 있다. 메모리 읽기와 디스크 복사를 모두 하므로 내용이 두 번 읽힌다.
`FileUtils.getPathFromCopyOfFileFromUri()`는 URI 기반 cache 디렉터리에 사본을 남긴다.
앱의 `pick()`는 bytes와 name만 반환하므로 사본을 정리하지 않는다. 내보내기용
`sanbo_exports` 정리 로직은 이 사본을 처리하지 않는다.

파일명 경로 이동 방어는 플러그인에 이미 있다. 단순히 외부 파일명이라는 이유로
경로 탈출 취약점으로 판정하지 않았다. 새 경계에서는 파일 크기와 실제 읽은 양을
모두 제한하고, 앱이 소유한 임시 파일만 정리해야 한다.

### 클립보드와 보관 설명

`lib/features/session_detail/session_detail_screen.dart`의 `_exportSession()`은
정밀 좌표, 필터링된 원본, 제외 정보, 메모를 NDJSON으로 복사한다. 전체 백업과 달리
민감 정보 안내가 없다. 요약 복사도 세션 메모와 저장한 장소 이름을 포함한다.
일반 사용자의 요약 공유와 원본 데이터 반출을 더 명확하게 구분할 필요가 있다.

[Android 공식 문서](https://developer.android.com/privacy-and-security/risks/secure-clipboard-handling)는
Android 10 이전의 백그라운드 접근과 민감 정보 미리보기 처리를 설명한다. 민감 표시만
추가해도 모든 접근이 차단되는 것은 아니다. 원본 경로는 파일로 내보내는 편이 낫다.

실패 기록의 원본 보관은 코드에 의도적으로 명시되어 있다. 이전의 원본 GPS 보존
요청과 연결되므로 이번 감사에서 임의 삭제하지 않았다. 보관 여부, 접근/삭제 방법,
보관 기간을 결정한 후 바꿔야 한다.

[Apple 파일 시스템 문서](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html)는
Documents와 Application Support가 기본 백업 대상이라고 설명한다. iOS 저장 위치만
옮겨서는 해결되지 않는다. OS 백업을 유지한다면 안내를 고치고, 제외한다면 사용자
복구 수단까지 함께 설계해야 한다.

### 측정 문제를 서둘러 고치지 않는 이유

provider speed 0을 무조건 정지로 처리하면 이전에 관측한 Android의 0m/s 응답 때문에
정상 걸음이 사라질 수 있다. 정확도 반경보다 작은 이동을 모두 버려도 느린 걸음이
누적되지 않는다. 왕복 흔들림 억제는 실제 왕복 산책과 원형 경로를 함께 검증해야 한다.
현재 고속 자동 제외 조건을 느슨하게 해서 이 문제를 덮는 방식도 부적절하다.

정지, 느린 걸음, 정상 보행, 실제 왕복, 신호 단절, 고속 이동을 같은 입력 집합으로
비교하는 후속 설계를 권한다. 과거 원본과 사용자 라벨은 보존하고 자동 재계산은
명시적인 별도 결정으로 다뤄야 한다.

## 이번에 결함으로 판정하지 않은 항목

- 건강 API 호출은 권한 인자를 생략하지만 현재 health 13.3.2의 기본값은 READ다.
  쓰기 권한을 요청한다고 주장하지 않는다.
- Android 위치 서비스는 외부 공개가 아니며 자동 백업 제외 규칙도 유지된다.
  이번에 OS 권한 우회를 새로 입증한 것은 아니다.
- 좌표와 시간의 기본 유효성 검사, 오래된 위치/미래 위치 차단, 세대가 지난 콜백
  차단, 샘플 저장 재시도, 백업 트랜잭션과 기존 ID 건너뛰기 방어는 존재한다.
- 지도 실패 메시지에는 키가 붙은 URI 대신 정리된 예외가 전달된다. 키가 APK에
  포함되는 기존 운영 위험은 여전히 남으며 새 비밀 유출과 구분한다.
- CI 토큰은 contents read이고 PR 코드를 공개 release 자격 증명으로 실행하는
  workflow는 없다. Actions의 tag 참조 고정과 native 의존성 SBOM/취약점 검사는
  추후 공급망 강화 후보이며, 이번에 확인한 탈취 사고는 아니다.
- 지도 HTTP 응답은 시간만 제한하고 크기는 제한하지 않는다. 정상 TLS 공급자의
  응답을 받는 경로이므로 악용 가능성을 확인한 백업 입력보다 낮은 순위로 둔다.
- Flutter/패키지 버전이 최신이 아니라는 사실만으로 무조건 일괄 갱신하지 않는다.

## 검증 기록과 한계

| 실행 | 결과 |
|---|---|
| `backup_boundary_probe_test.dart` | 4개 문제 동작 확인 |
| `privacy_measurement_probe_test.dart`의 측정/보관 진단 | 2개 문제 동작 확인 |
| 클립보드 위젯 진단 단독 실행 | 1개 문제 동작 확인 |
| [OSV batch API](https://google.github.io/osv.dev/api/) | Pub 125개, 일치 0개, 추가 페이지 0개 |

클립보드 진단의 첫 실행은 테스트의 fake clock 안에서 DB 비동기를 기다려 timeout이
났다. 다음 시도도 대기하여 중단했다. 실제 DB 로딩을 `runAsync` 안에서 완료한 뒤
동일한 상세 화면에 결과를 공급하자 1개 검사가 통과했다. 제품 결함으로 집계하지 않는다.

실제 악성 ContentProvider, 구형 Android의 다른 앱 클립보드 접근, iCloud 백업,
물리 기기의 GPS/배터리, native 의존성 전체 CVE 검사는 미실행이다. 인증 계정의
CARTO 현재 사용량과 과금 조건을 이번에 다시 읽지 않았으며 10월 18일 관측을 현재
수치로 표현하지 않는다.
