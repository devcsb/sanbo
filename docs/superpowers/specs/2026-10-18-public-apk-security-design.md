# 공개 APK 보안 개선 설계

작성일 2026-10-18. 상태: 사용자 검토 전. [조사 증거](../../security/2026-10-18-public-apk-security-review.md)를 기준으로 한다.

## 의도와 사용자 결정

공개 APK를 다른 사용자가 분석해도 개발자 개인정보와 서명 비밀이 유출되지 않도록 하고, 지도 키 재사용의 실제 한계를 설명한다. 지도 인증 실패가 정상 지도처럼 캐시되거나 오류 상태를 놓치는 문제를 고친다. 기록 기능과 기존 업데이트 호환성을 유지한다.

사용자는 REA를 활용한 공개 APK 조사와 필요한 조치를 요청했고, 광고 도입을 고려한다고 밝혔다. 광고 구현, 서버 도입, 유료 서비스 구매, 건강 데이터를 광고에 사용하는 운영 방식은 승인한 적이 없다. 이하 권고는 구현자의 제안이며 아직 사용자 결정이 아니다.

이번 조사는 직접 실행했다. 사용자 AGENTS가 Codex의 재위임을 금지하므로 별도 독립 모델 검토를 했다고 주장하지 않는다. 구현 전 계획과 검증 범위를 문서화한다.

## 접근 선택

| 접근 | 얻는 것 | 남는 위험/비용 |
|---|---|---|
| **현재 구조에서 검증된 결함 수정과 사용량 관리 준비 (권고)** | 인증 안내 감지, 개인정보 경로 제거, APK 보안 검사, 정확한 안내, 공급자 제한 준비. 별도 서버 없음. | 클라이언트 키는 계속 추출 가능하다. 요청 제한과 초과 처리의 계정 확인이 필요하다. |
| 앱 증명을 검증하는 인증 프록시 | 서버에서 요청률과 전체 한도를 관리하고 제공자 키를 앱에서 제거할 수 있다. | 신규 운영비, 장애 지점, 위치/IP 취급 책임, 증명과 우회 대응이 생긴다. 단순 공개 프록시는 해결책이 아니다. |
| 지도 공급자 변경 또는 오프라인 지도 | 현재 CARTO 키 의존을 줄일 수 있다. | 새 공급자 약관/비용/기술 검증과 기능 변경이 필요하다. 공용 OSM 타일로 바꾸는 것만으로 무제한 무료 사용이 보장되지 않는다. |

권고 범위는 첫 번째 접근이다. 강한 자동 남용 방지와 비용 보장을 달성했다고 주장하지 않는다. 키 재추출을 막는 것이 필수 조건이면 두 번째 접근을 별도 프로젝트로 설계해야 한다.

## 제품 요구사항

1. 도로/지명이 있는 현재 정상 CARTO 지도는 유지한다. 타일 인증 실패와 공급자 안내를 구분해 사용자에게 상태를 알린다. 공급자 안내 이미지와 attribution은 숨기거나 우회하지 않는다.
2. 지도 실패/정지 상태에서도 산책 시작/종료, GPS 로컬 저장, 거리/속도 계산, 경로 선분과 기록 조회가 계속 동작해야 한다.
3. 새 배포 산출물에서 개발자 홈 디렉터리 경로, 등록 이메일, 서명 개인키/설정 파일이 발견되지 않아야 한다. 보안 검사를 통과하기 위해 공개 클라이언트 키까지 비밀이라고 선언하지 않는다.
4. 설정의 지도 안내는 ‘지도 화면을 열면 표시 영역과 IP 주소 등 요청 정보가 CARTO에 전달되며, 이 정보로 표시 위치를 추정할 수 있어요’처럼 전달 범위와 의미를 설명한다. OS 주소 제안의 사용자 요청 전송과 로컬 원본 보관을 구분한다.
5. README와 릴리스 안내에 클라이언트 키 추출 가능성, 사용량 합산, 광고 도입 전 상업용 분류 변경, 사용자 내보내기 파일의 민감성을 설명한다.
6. 현재 스키마, 원본 GPS, 사용자 확정 라벨, 제외 취소, 서명 인증서는 변경하지 않는다. 광고 SDK/맞춤광고/새 서버도 추가하지 않는다.

## 기술 설계

### A. 인증 안내 판별

현재 관측한 `"wm-...-light"` 계열 ETag를 좁게 인식한다. 특정 해시 값의 완전 일치를 제거하고 strong/weak ETag 표현을 함께 검증한다. 정상 타일, ETag가 없거나 관계없는 응답은 기존대로 처리한다. 공급자 내부 ETag가 영구 계약이라는 가정은 하지 않는다.

현재 구조의 `onAuthenticationNotice` 흐름을 재사용해 화면 실패 상태와 안내 타일 캐시 제외를 유지한다. 원래 PNG는 반환한다. 401/403/429/5xx, 전송/읽기 오류에 대한 키/URL 제거도 유지한다. 일반 이미지 분석, OCR, 임의 HTTP200을 실패로 취급하는 새 휴리스틱은 넣지 않는다.

실제 2026-10-18 무키 응답으로 실패한 진단을 회귀 테스트로 만든다. normal/strong/weak/missing ETag와 캐시 회복, 진단 메시지에 키가 없는지도 검사한다. 외부 서비스가 바뀌는 부분은 실제 정상/invalid 키의 최종 화면 검사를 추가한다.

### B. 빌드 경로와 배포물 검사

생성 plugin registrant에 로컬 절대 경로가 남는 원인을 빌드 위치에서 제거한다. 중립 임시 경로에 확정된 소스를 준비해 릴리스 빌드를 수행하고 생성 파일을 직접 바이너리 패치하지 않는다. 필요한 서명/지도 설정은 기존 private 입력으로 전달하고 임시 사본은 제한된 권한과 정리 절차를 적용한다. 사용자 홈과 원래 작업 폴더는 출력물에 재포장하지 않는다.

별도 검사 스크립트는 명시된 APK/AAB만 읽고 zip entry와 네이티브 페이로드를 검사한다. 개인 경로, 키스토어/비밀 설정, private-key PEM, 알려진 개인 이메일 등의 검사는 값이나 주변 문자열을 출력하지 않고 항목명과 검출 여부만 반환한다. CARTO 클라이언트 키 존재 여부는 기대한 빌드 설정과 일치하는지 비공개로 확인하되 공개 로그에 노출하지 않는다. 앱 동작/서명 확인을 대체하지 않는다.

새 APK를 다시 내려받아 같은 검사를 수행하고 해시를 릴리스 증거에 남긴다. 이 방식으로 경로가 실제 제거되지 않으면 원인을 좁히며 성공으로 보고하지 않는다. 난독화를 비밀 보호 대책으로 추가하지 않는다.

### C. 키 제한과 운영 준비

상업용 분류, 사용량, 초과 시 차단/청구 조건, 알림, 허용 가능한 제한을 CARTO dashboard/공급자에서 확인하는 운영 체크를 작성한다. 대화와 Git에는 키 값을 남기지 않는다. 광고가 없는 현재 배포와 광고가 들어가는 미래 배포를 구분한다. 임의로 결제 정보를 넣거나 유료 계약을 구매하지 않는다.

모바일 제한은 Android `X-Android-Package`/`X-Android-Cert`, iOS `X-Ios-Bundle-Identifier`를 공급자가 안내한 값으로 보낼 때만 적용한다. 식별자는 두 플랫폼 모두 `com.sanbo.sanbo`다. Android 인증서 값의 정확한 형식은 dashboard에서 확인한 뒤 빌드 입력에 명시하며 SHA-1/SHA-256 형식을 추측하지 않는다. 여기서는 계정 설정을 확인하기 전 임의 인증 헤더를 구현하지 않는다.

계정 확인 뒤 별도 키와 새 헤더를 포함한 후보를 검증하고 제한을 켠다. 기존 v0.9.3은 식별 헤더를 보내지 않으므로 기존 키에 즉시 새 제한을 걸거나 폐기하면 기존 사용자 지도가 깨진다. 교체 키의 정상/무헤더/잘못된 헤더/복제한 정확한 헤더 대조와 전환 일정을 확인한 뒤 진행한다. 계정 접근을 못 하면 이 항목은 미확인으로 남기고 해결됐다고 표시하지 않는다.

헤더는 공개되어 복제가 가능하다. 따라서 헤더 제한을 앱의 진위를 입증하는 보안 경계로 표현하지 않는다. 난독화, 키 교체, 로컬 캐시만으로 제삼자의 직접 요청을 차단했다고 주장하지 않는다.

### D. 광고와 개인정보 안내

이번에는 광고를 추가하지 않는다. 향후 광고 PR의 선행 조건을 문서화한다. CARTO 분류 변경, 광고 SDK 수집 항목과 위치 접근 확인, 개인정보처리방침/스토어 신고, 필요한 동의 처리가 그 대상이다. 걸음 수와 건강 데이터를 광고 요청이나 타기팅 입력으로 넘기지 않는 구조를 명시한다.

현행 저장소의 일반 `Text` 표시, 매개변수화된 SQL, 백업 형식/크기/좌표/연결 검증, 트랜잭션 취소를 유지한다. 수동 백업 암호화는 이번 범위에서 새 형식과 비밀번호 복구 체계로 확대하지 않는다. 현재 평문 JSON과 정밀 위치 포함 사실을 명확히 안내한다.

## 완료 조건

- 실제 무키 응답의 인증 안내 회귀가 실패에서 통과로 바뀐다. 정상 지도/실패 회복과 키 없는 진단을 확인한다.
- 새 서명 APK/AAB에 개발자 홈 경로/개인 이메일/서명 비밀이 검출되지 않고, 기존 인증서와 앱 업데이트 호환성이 유지된다.
- 새 공개 산출물 기준 해시와 비디버그/backup 설정, 저장소 경계, 고속 제외/기록 데이터 보존을 확인한다.
- 계정의 한도/차단/결제 조건은 실제 확인 결과를 남긴다. 확인하지 못한 운영 항목을 완료로 표시하지 않는다.
- 제품 안내와 README가 검사 결과 및 공급자 최신 조건과 모순되지 않는다.
- 해당 변경의 테스트, 정적 분석, 네이티브/릴리스 게이트를 필요한 순서로 실행한다. 이미 통과한 동일 게이트를 근거 없이 반복하지 않는다.
- PR과 릴리스에는 남은 클라이언트 키 재사용 위험, 모바일 헤더의 한계와 미검증 범위를 명시한다. 병합/공개는 구체적인 후보와 최종 결과를 제공한 뒤 기존 사용자 승인 범위에 맞춰 처리한다.

승인 뒤 `superpowers:writing-plans`로 이 범위를 실행 가능한 구현 계획으로 나눈다.
