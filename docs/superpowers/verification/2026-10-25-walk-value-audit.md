# 산보의 사용 이유와 측정 신뢰성 추가 검토

2026-10-25. 기준 제품 소스는 `4b64b2c`이며 검토 중 제품 코드는 바꾸지 않았다.
보안 검토 뒤 도착한 사용자의 실제 불편 다섯 가지를 우선순위 판단 근거로 삼는다.
이 문서는 조사 결과와 방향 제안이며 구현 승인된 PRD/TRD가 아니다.

## 사용자가 설명한 문제

1. 시중의 다른 앱 대신 산보를 사용할 이유가 잘 드러나지 않는다.
2. 앱이 무겁고 배터리를 많이 쓰는 듯하지만 이유를 알기 어렵다.
3. 기록을 끄지 않고 출근하거나 차/전철을 타면 산책과 차량 이동이 섞인다.
4. 산책을 마쳐도 얼마나 걸었고 자신에게 어떤 효과가 있었는지 체감하기 어렵다.
   칼로리, 수명에 해당하는 시간 등은 효용을 표현하는 예로 들었다.
5. 종료 후 속도가 거리/이동 시간으로 계산한 값과 다르게 느껴지는 경우가 있다.
   과거 순간 속도/최고 속도가 저장된 것은 아닌지 의심했다.

## 현재 제품 방향과의 차이

기존 PRD는 경로, 멈춘 이유, 활동 타임라인을 돌아보는 회상을 중심 가치로 정의했다.
칼로리 중심 피트니스와 상시 라이프로그는 비목표다. 이번 사용자 설명은 걷기 분리의
정확성, 낮은 사용 부담, 산책 후 체감 효과에 더 무게를 둔다. 기존 문구 몇 개만
바꾸면 해결되는 문제로 취급하지 않는다. 사용자 요구가 기존 문서보다 우선한다.

방향 제안은 **기록을 깜빡 꺼도 실제 걸은 양을 이해하고 바로잡기 쉬운 개인 산책 기록**이다.
아직 이 성능을 달성했다고 홍보하지 않는다. 항상 알아서 걷기를 완벽하게 구분한다거나
배터리를 거의 쓰지 않는다는 약속도 하지 않는다.

## 추가로 실행한 진단

저장소 밖 `walk_value_probe_test.dart`의 5개 진단을 실행했고 모두 예상 동작을 확인했다.
실제 GPS/배터리 측정이 아닌 합성 위치와 현재 정책 함수의 검사다.

| 항목 | 결과 | 해석 |
|---|---|---|
| 약 40km/h로 2분 이동, 정확도 5m | 1,334.3m 경로에 자동 제외 범위 1개 | 좋은 GPS에서 고속 제외가 작동한다. |
| 같은 이동, 정확도 30m | 자동 제외 0개 | 위치 자체는 거리 필터를 통과하지만 자동 제외의 25m 기준에서 빠져 차량 거리가 남는다. |
| 한 분 안의 걷기 20초 + 빠른 이동 40초, 정확도 5m | 약 420m 모두 포함, 자동 제외 0개 | 분 전체에서 고속이 확인되어야 하는 정책이 전환 구간의 차량 이동까지 남긴다. |
| 균형 모드에서 16초간 위치 콜백 없음 | Fused → LocationManager 복구 결정 | 위치 간격 8초 + 8초 후 복구한다. 5m distance filter 때문에 정지 중 콜백이 없을 수도 있으므로 무수신만으로 장애를 단정하기 어렵다. 실제 배터리 영향은 미측정이다. |
| 1km, 이동 10분 | 완료 평균 6km/h | 화면의 전체 시간 예시가 20분이면 사용자가 계산한 3km/h와 달라 보인다. 현재 완료 함수는 순간/최고 속도 필드를 받지 않는다. |

### 차량 혼입은 기존 정책의 한계다

`AutomaticRouteExclusionPolicy`는 신뢰도가 충분한 고속 구간만 제외한다. 이전에
승인한 보수적인 기준대로 동작하지만, 지하철의 신호 저하, 차량 전환이 걸친 분,
정체 구간을 ‘실제로 걸은 양’에서 완전히 분리하지는 못한다.

분석 결과 신뢰도가 낮다고 원본 위치를 모두 지우는 접근은 적절하지 않다. 걷기,
차량 이동, 정지, 판단할 수 없는 구간을 구분하고, 불확실한 구간은 사용자 확인으로
바꿀 수 있어야 한다. 원본과 확정 라벨 보존, 제외 취소는 계속 유지해야 한다.

초 단위 전환을 지원하려면 자동 제외 감지뿐 아니라 지도, 집계, 분 타임라인,
재생, export의 같은 범위 해석도 바꿔야 한다. 현재 `user_exclusion_id` 하나로 분의
상태를 표시하므로 일부만 제외된 분을 통째로 0으로 보여 주지 않도록 설계해야 한다.
25m 기준을 단순히 높이거나 10km/h 기준만 낮추는 수정으로 끝내지 않는다.

차량에서 내려 다시 걸을 때 한 산책을 이어갈지, 별도 산책으로 나눌지는 사용자에게
질문한 상태다. 이 답은 세션 모델, 자동 종료, 결과 요약과 배터리 정책을 바꾼다.

### 배터리에는 실제 측정이 빠져 있다

균형 모드는 high accuracy, 8초, 5m이고 CPU WakeLock은 꺼져 있다. 정밀 모드만
WakeLock을 켠다. foreground의 1초 UI ticker는 background 진입 시 멈추므로
그 timer가 계속 화면을 그린다고 판정하지 않는다. 건강 데이터는 요청 시 읽는다.

반면 위치 콜백의 짧은 침묵에도 provider를 전환하는 정책은 측정 후보이다. 완전히
정지한 경우, 실외 정상 걷기, 터널/지하철을 나눠 provider 전환 수, GPS 사용 시간,
WakeLock, CPU와 배터리 감소를 같은 기기에서 비교해야 한다. 복구를 무조건 없애면
이전에 대응한 삼성 Fused 장애가 다시 발생할 수 있다.

`LocationEnergyPolicy`는 현재 제품에서 호출되지 않고 자체 테스트만 있다. 따라서
배터리 잔량에 따라 자동으로 절전하거나 안내한다고 사용자에게 설명하면 안 된다.
사용되지 않는 정책을 연결할 필요가 있는지, 제거할지 구현 설계에서 정한다.
분석용 로컬 카운터는 좌표나 건강 정보를 외부 전송하지 않는 범위로 유지한다.

### 속도는 식과 입력을 분리해서 확인해야 한다

완료 화면은 `completedAverageSpeedMps(totalDistanceM, movingTimeS)`를 호출한다.
`avg_speed_mps`에 과거 값이 남아 있어도 현재 완료 화면이 그 값을 그대로 읽지는 않는다.
화면의 평균은 `거리(m) / 이동 시간(s) × 3.6`이다.

다만 주요 지표에는 ‘시간’으로 정지/신호 공백을 포함하는 세션 시간이 먼저 나오고,
이동 시간은 아래 세부 정보에 있다. 반올림된 km와 초 단위 시간 때문에 작은 차이가
생길 수도 있다. 완료 평균의 이름, 분모와 포함/제외 범위를 함께 알릴 필요가 있다.

사용자가 겪은 구체적 기록의 설치 버전, 표시한 거리/시간/속도를 아직 받지 않았다.
따라서 실제 사례를 단순한 UI 혼동으로 확정하지 않는다. 백업/과거 DB의 잘못된 집계,
차량 포함, GPS 흔들림도 가능한 원인이다. 기존 기록을 몰래 일괄 재계산하지 않는다.

## 다른 앱과 비교할 때 남는 과제

공식 설명을 확인한 범위에서 Samsung Health는 걷기 시간/거리/칼로리와 목표를,
Pacer는 걸음/거리/칼로리와 GPS 기록을, Strava는 시간/거리/활동 횟수 목표를 제공한다.
아래 출처는 기능 소개이며 실제 정확성이나 전력 소비를 비교한 벤치마크가 아니다.

- [Samsung Health trackers](https://www.samsung.com/us/support/answer/ANS10001351/)
- [Pacer walking app](https://www.mypacer.com/walking-app)
- [Strava app goals](https://support.strava.com/en-us/articles/15401694-goals-on-the-strava-app)

칼로리 숫자 하나나 목표 진행률을 추가하는 것만으로 산보의 사용 이유를 만들기는 어렵다.
제안하는 차별점은 일상 이동이 섞여도 걷기만 분리하고, 불확실성을 설명하며,
계정 가입 없이 원본을 기기에 보관하고 직접 수정/반출할 수 있는 경험이다.
경쟁 제품에 비슷한 기능이 전혀 없다는 뜻은 아니다.

## 효용 표현의 제안

먼저 확실히 계산할 수 있는 걸은 시간/거리, 제외한 이동, 이번 주 누적과 자신의
이전 기록 대비 변화를 연결한다. 쉬거나 짧게 걸은 날을 실패로 표현하지 않는다.
명목상의 전체 켜둔 시간을 걷기 성과로 부풀리지 않는다.

칼로리를 넣는다면 추정 방식과 필요한 입력을 정하고 추정치임을 밝힌다. 체중을
임의로 가정하거나 차량/불확실 구간을 운동량으로 환산하지 않는다. ‘수명 +몇 분’은
현재 앱이 개인별로 계산할 근거가 없으므로 확정 보상으로 제시하지 않는 방향을 제안한다.
실제 효과를 과장한 문구를 추가하기보다 사용자가 이해하는 성과를 먼저 만든다.

구체적인 종료 화면과 카피는 시각 시안을 보여 준 뒤 정한다. 아직 화면/기능을
구현하지 않았으며 이 문서의 제안을 사용자 합의로 간주하지 않는다.

## 제안하는 작업 순서

1. 확인한 백업 입력/개인정보 반출 문제를 범위가 작은 보안 수정으로 막는다.
2. 차량 후 걷기 처리와 걷기/불확실 구간 집계 계약을 정하고 속도 설명을 일치시킨다.
   좋은 GPS, 나쁜 GPS, 느린 걸음, 왕복, 차량 정체/승하차를 같은 검증 집합에 넣는다.
3. 배터리 기준값과 provider 복구를 측정하며 기록 정책을 조정한다. 시뮬레이터 결과로
   실기기 절전 효과를 주장하지 않는다.
4. 검증한 산책량을 바탕으로 첫 경험과 종료 후 효용을 설계한다. 그때 PRD/TRD의
   기존 회상 중심 가정과 비목표도 사용자 요구에 맞게 수정한다.

이 순서와 차량 후 기록 방식은 아직 확정 전이다. 제품 전면 개편, 보안 수정, 측정
정책을 하나의 거대한 PR로 합치지 않는 방향을 제안한다.
